# Avito: кандидатогенерация для поиска услуг (Recall@50)

Решение тестового задания: по поисковому запросу выбрать из корпуса `benchmark_items.parquet` до 50 объявлений так, чтобы в них попало как можно больше подходящих.

Весь код, EDA, валидация, дообучение моделей, подбор весов, бустинг, проверки и описание решения находятся в ноутбуке [solution.ipynb](solution.ipynb). Ноутбук сохранен вместе с выводами последнего запуска.

## Подход

Два этапа, как в обычном поисковом каскаде.

**Первый этап.** Для каждого запроса скор считается сразу по всем объявлениям корпуса как взвешенная сумма сигналов:

- **BM25** по заголовку + описанию + параметрам объявления и отдельно по заголовку (слова со стеммингом Snowball);
- **локация**: log P(локация объявления | локация поиска), вероятности посчитаны по train. В 83% пар train локации совпадают, остальное в основном "регион -> город";
- **нелокальность запроса**: по похожим запросам из train считается, как часто люди выбирали объявление в другом месте (базы отдыха, межгород, онлайн-услуги). Для таких запросов штраф за локацию ослабляется;
- **расстояние** от типичной точки локации поиска до координат объявления;
- **фильтры**: "Вид услуги ..." и "Тип услуги ..." из `search_infm_params_text` сверяются с `item_infm_params_text` (в train совпадают в 98% пар);
- **категория**: совпадает ли категория объявления с `search_category`. У 9% запросов benchmark поиск без категории (`search_category = 0`), и для них в корпусе есть подходящие объявления из других категорий, поэтому для таких запросов штрафа за категорию нет;
- **подкатегория**: распределение `item_microcat_id` по 20 самым похожим запросам из train;
- **расширение запроса**: заголовки объявлений, выбранных по похожим запросам в train, сравниваются с заголовками корпуса (TF-IDF);
- **эмбеддинги** готовой модели `sergeyzh/rubert-tiny-turbo`;
- **эмбеддинги двух дообученных моделей**: `rubert-tiny-turbo` и `sergeyzh/rubert-mini-frida`, дообученные на парах "запрос - выбранное объявление" из train (одна эпоха на CPU, в батче остальные объявления служат отрицательными примерами).

Веса подобраны перебором по координатам на выборке A.

**Второй этап.** Кандидаты из трех источников: 200 лучших по взвешенной сумме, 200 лучших по той же сумме с ослабленной локацией и 150 лучших только по тексту (около 330 на запрос, нужное объявление среди них в 97% случаев). Их переранжирует `HistGradientBoostingClassifier` из scikit-learn (200 деревьев, без ранней остановки). Признаки: все сигналы, скор взвешенной суммы и место кандидата по нему, отставание кандидата от лучшего в запросе по каждому текстовому сигналу, место кандидата по каждому сигналу (при равных значениях среднее место), число кандидатов в "своей" локации, число слов в запросе, наличие фильтров, доля запросов из этого города в train. Обучаются две модели, со всеми признаками и без мест кандидата, ответ - среднее их вероятностей, в ответ идут 50 лучших. Бустинг учится на выборке A (для ответа - на A и B вместе). На B он дает 0.917 против 0.887 у одной взвешенной суммы.

## Валидация

- `train.parquet` делится по уникальным комбинациям всех `search_*` полей (40% в валидацию), чтобы одна комбинация не попала в обе части. Все объявления, выбранные по одной комбинации, объединены в один запрос с несколькими релевантными `item_id`.
- Состав валидационных выборок A и B (по ~3000 запросов, по одному на текст) подобран таким же, как в benchmark, по трем признакам: насколько часто текст встречался в train (37% новых, знакомые в основном редкие), есть ли фильтры (63% без фильтров) и из крупного ли города запрос (22% из двух самых частых локаций). При случайном выборе валидационные запросы получались "легче" benchmark.
- Корпус benchmark собран вокруг самих запросов: рядом с каждым запросом (в той же локации и по смыслу) много похожих объявлений. Поэтому в корпус для валидации кроме `benchmark_items` и релевантных объявлений добавляются "похожие" объявления: для каждого валидационного запроса 30 лучших по BM25 и 30 лучших по эмбеддингам из подходящих локаций, только из объявлений, которых нет в обучающей части. Всего около 270 тыс. объявлений.
- Вся статистика по train и дообучение моделей на валидации используют только обучающую часть. Для финального ответа статистика считается по всему train, и обе модели дообучаются заново на всем train.
- Калибровка: отправленные версии на платформе получили 0.877, 0.882, 0.898, 0.898, 0.900 и 0.905, на выборке B - 0.880, 0.892, 0.902, 0.910, 0.913 и 0.917. Валидация завышает на 0.3-1.2 пункта и хорошо ловит крупные изменения, а улучшение бустинга в четвертой версии на платформу не перенеслось.

## Как запустить

Windows:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Linux / macOS:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Положить `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet` в папку `dataset/` и выполнить ноутбук целиком (Run All) или из консоли:

```bash
jupyter nbconvert --to notebook --execute --inplace solution.ipynb --ExecutePreprocessor.timeout=-1
```

В конце ноутбук пишет `answer.csv` в корень репозитория. На 8-ядерном CPU без GPU и 32 ГБ памяти прогон с нуля занимает около 4 часов. Больше половины времени уходит на дообучение четырех моделей (две модели, каждая на обучающей части для валидации и на всем train для ответа). Эмбеддинги и дообученные модели сохраняются в `cache/`, повторный прогон с готовым кэшем занимает около 80 минут. На пике ноутбук занимает около 20 ГБ оперативной памяти, поэтому параллельно с ним лучше ничего тяжелого не запускать. При первом запуске модели `sergeyzh/rubert-tiny-turbo` (~120 МБ) и `sergeyzh/rubert-mini-frida` (~130 МБ) скачиваются с Hugging Face, дальше все работает локально, без обращений к внешним API.

## Проверки ответа

В разделе 12 ноутбука `answer.csv` читается обратно и проверяется: две колонки `query_id,answer`, строка на каждый `query_id` без лишних и повторов, не больше 50 `item_id` без повторов, все `item_id` есть в корпусе, разделитель ровно один пробел, ID остались строками. Отдельно проверяются байты файла: переводы строк только `\n` (на Windows pandas по умолчанию пишет `\r\n`, и `\r` мог бы прилипнуть к последнему `item_id` в строке), нет BOM, нет пробелов по краям, все `item_id` строчными буквами. Там же разобраны пограничные случаи: пустые фильтры, запросы из одного слова, запросы без совпадений по словам, редкие категории, запросы без категории, дубли объявлений, необычные символы.

## Воспроизводимость

Случайность есть в сплите, в дообучении моделей и в бустинге. Везде зафиксирован `SEED = 42`, порядок батчей задается через `random.Random(SEED)`, на время обучения включен детерминированный режим PyTorch, у бустинга задан `random_state`. Ноутбук выполнялся целиком два раза, и оба раза получился один и тот же `answer.csv`, md5 печатается в конце ноутбука: `eb7e9bfc5a7ca03a778e3332c1cc6cb6`. Все эмбеддинги и дообученные модели в кэше были посчитаны этим же ноутбуком с пустого кэша, а для предыдущей версии отдельно проверялось, что заново дообученные модели для финального ответа дают тот же файл байт в байт. Проверялось на Windows 10, Python 3.14, версии библиотек в `requirements.txt`. На другом железе или с другими версиями PyTorch вычисления с плавающей точкой могут отличаться в последних знаках, и тогда могут поменяться отдельные объявления на границе топ-50.

## Библиотеки и модели

pandas, numpy, scipy, pyarrow, scikit-learn (CountVectorizer, TfidfVectorizer, HistGradientBoostingClassifier), snowballstemmer, PyTorch, sentence-transformers, модели [sergeyzh/rubert-tiny-turbo](https://huggingface.co/sergeyzh/rubert-tiny-turbo) и [sergeyzh/rubert-mini-frida](https://huggingface.co/sergeyzh/rubert-mini-frida).
